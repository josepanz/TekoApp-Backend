01

SDK de Android sin instalar Android Studio

Flutter necesita el Android SDK para compilar, no el IDE completo. Se instalan solo las "command-line tools" (unos MB, no unos GB).

  1. Descargar "Command line tools only" para Windows desde la página oficial de Android Studio (sección "Command line tools only", más abajo que el instalador completo — no descargar ese).
  2. Descomprimir el zip de forma que quede exactamente en esta ruta (Android exige el nombre de carpeta latest, si no se respeta sdkmanager no lo encuentra):
    powershell
    %LOCALAPPDATA%\Android\sdk\cmdline-tools\latest\bin\sdkmanager.bat
  3. Configurar las variables de entorno (una vez, quedan permanentes):
    powershell
    setx ANDROID_HOME "%LOCALAPPDATA%\Android\sdk"
setx PATH "%PATH%;%LOCALAPPDATA%\Android\sdk\platform-tools;%LOCALAPPDATA%\Android\sdk\cmdline-tools\latest\bin"
    Cerrar y volver a abrir la terminal para que tomen efecto.
  4. Aceptar licencias e instalar lo mínimo necesario:
    powershell
    sdkmanager --licenses
sdkmanager "platform-tools" "platforms;android-34" "build-tools;34.0.0"
flutter config --android-sdk "%ANDROID_HOME%"
  5. Verificar con flutter doctor -v. La línea de Android toolchain debe quedar en verde. La línea de Android Studio va a seguir en rojo/amarillo — ignorarla, no hace falta para flutter run en un dispositivo físico.
02

Conectar el teléfono al backend

Como el teléfono va por cable, la forma más simple y confiable no es la WiFi — es adb reverse: el teléfono le pega a localhost y Android lo reenvía a la PC por el mismo USB. Cero configuración de firewall, cero IPs que cambian.

Opción recomendada — USB con adb reverse

  1. Conectar el cable. En el teléfono aparece un diálogo "¿Permitir depuración USB?" → aceptar (marcar "siempre desde esta compu" para no repetirlo).
  2. Confirmar que Windows lo ve autorizado:
    powershell
    adb devices
# debe decir "device", no "unauthorized" ni "offline"
  3. Reenviar el puerto del backend (repetir cada vez que se desconecta/reconecta el cable o se reinicia la PC — no es persistente):
    powershell
    adb reverse tcp:3000 tcp:3000
  4. Con esto, la URL del backend desde el punto de vista del teléfono es http://127.0.0.1:3000 — se usa tal cual en la Fase 5.

Alternativa — misma red WiFi (sin cable, o para probar condiciones de red reales)

  1. Sacar la IP LAN de la PC: ipconfig → buscar "Dirección IPv4" del adaptador WiFi (ej. 192.168.1.50).
  2. Abrir el puerto 3000 en el Firewall de Windows para conexiones entrantes desde la red (Panel de control → Firewall de Windows Defender → Configuración avanzada → Regla de entrada nueva → Puerto → TCP 3000 → Permitir).
  3. Usar http://192.168.1.50:3000 (IP real) como base URL.

Solo si hace falta Si el teléfono y la PC alguna vez NO están en la misma red (datos móviles, WiFi de invitados que aísla dispositivos), Tailscale es gratis y arma una red privada entre ambos sin abrir puertos al público — se instala la app en el teléfono y un cliente en la PC, y se usa la IP 100.x.x.x que asigna en vez de la LAN. No hace falta en el caso normal (misma WiFi), queda solo como plan B.

03

Backend local + cada servicio en su capa gratis

El repo ya trae docker-compose.yml con Postgres, MongoDB y Redis. Se agregó un servicio MinIO (S3 compatible, corre en la PC, cero cuenta AWS) para que el almacenamiento de archivos también sea 100% local y gratis en este modo.

powershell
docker compose up -d postgres mongodb redis minio
# backend corre nativo con hot-reload, no dentro del compose:
pnpm install
pnpm run seed
pnpm run start:dev

Abrir http://localhost:9001 (consola de MinIO, usuario/clave tekoapp / tekoapp123) y crear un bucket llamado tekoapp-uploads una sola vez.

04

Usuarios y perfiles de prueba

  1. powershell
    pnpm run seed
    Deja lo mínimo para que la app arranque: catálogo base, el cliente Basic Auth de Web, y el de Mobile (tekoapp-mobile — sin esto, el login desde la app falla siempre con INVALID_CLIENT_ID). Usuario admin: admin@tekoapp.com.py / Tekoapp123!.
  2. powershell
    pnpm run seed:dummy
    Puebla clientes, profesionales, servicios, pagos, calificaciones y promociones ficticios para navegar la app ya "cargada". Todos los usuarios dummy comparten la misma contraseña: Tekoapp123!. El script no es idempotente — correrlo una sola vez sobre una base limpia.
  3. Para elegir con qué email loguearse (cliente o profesional específico), abrir Prisma Studio — ya viene con el proyecto, gratis, sin cuenta:
    powershell
    pnpm exec prisma studio
    Mirar la tabla Users, cualquier fila con @example.com es un dummy — password siempre Tekoapp123!.
05

Correr la app en el Android

Con el backend corriendo (Fase 3), el puerto reenviado (Fase 2) y usuarios sembrados (Fase 4):

  1. Confirmar que Flutter ve el teléfono: flutter devices — anotar el device-id que aparece.
  2. TekoApp-Frontend-Mobile/dart_defines.local.json (gitignored, ya creado) trae API_BASE_URL, BASIC_AUTH_CLIENT_ID y el mismo BASIC_AUTH_CLIENT_SECRET que MOBILE_CLIENT_SECRET en el .env del backend — si se cambia uno, cambiar el otro y volver a correr pnpm run seed.
  3. Correr la app:
    powershell — TekoApp-Frontend-Mobile
    flutter run --dart-define-from-file=dart_defines.local.json -d <device-id>
    Si se usó la alternativa por WiFi de la Fase 2, editar la IP dentro de ese mismo archivo JSON en vez de 127.0.0.1.
06

iOS en la Mac (misma red)

Distinto mecanismo al de Android: el Simulator de Xcode corre en la propia Mac y accede directo a la red — no hay alias 10.0.2.2 (eso es solo del emulador Android) ni hace falta adb reverse (eso es solo para USB/Android).

  1. La Mac tiene que estar en la misma WiFi que la PC del backend (no por cable a esta PC — no aplica el truco de la Fase 2).
  2. Abrir el firewall del backend igual que en la alternativa WiFi de la Fase 2 (puerto 3000 entrante).
  3. Desde la Mac: flutter run --dart-define=API_BASE_URL=http://<IP-LAN-de-la-PC>:3000/tekoapp-backend/api --dart-define=BASIC_AUTH_CLIENT_ID=tekoapp-mobile --dart-define=BASIC_AUTH_CLIENT_SECRET=<mismo valor que MOBILE_CLIENT_SECRET>.
07

Demo pública en internet opcional

Solo si en algún momento hace falta mandar un link a alguien fuera de la red — no hace falta para nada de lo de arriba. Acá el backend deja de poder usar Docker local: todo tiene que ser alcanzable desde internet.

Backend → Render.com (free)

Web Service gratis desde el Dockerfile del repo. Se "duerme" tras 15 min sin tráfico y tarda ~30-50s en despertar en el próximo request — normal en el plan free, no es un bug.

Postgres → Neon (free)

No usar el Postgres free de Render — se borra a los 30 días. Neon (o Supabase) no expira en su capa free.

MongoDB → Atlas M0 (free)

512MB, no expira. MONGODB_URI con el connection string que da Atlas.

Redis → Upstash (free)

Da un solo endpoint rediss://usuario:clave@host:puerto — separar en REDIS_HOST/REDIS_PORT/REDIS_PASSWORD.

Archivos → Cloudflare R2

10GB gratis, sin cobro por egreso — a diferencia de MinIO, Cloudflare sí pide tarjeta para activar R2 aunque el uso se mantenga gratis.

Web → Vercel (free)

Hecho a medida para Next.js. Variable de entorno apuntando a la URL pública del backend en Render; agregar esa misma URL de Vercel a ALLOWED_ORIGINS/FRONTEND_URL del backend.

Mobile no entra en este modo — no hay build firmado ni tienda todavía, sigue siendo local por USB (Fase 5) o Mac+Simulator (Fase 6) contra el backend que se elija (local o el de Render).

Qué se tocó en el código para esto (2026-08-08)

  • TekoApp-Backend/src/modules/storage/storage.module.ts + config-loader.ts — soporte opcional de S3_ENDPOINT/S3_FORCE_PATH_STYLE (aditivo, sin setear se comporta exactamente igual que antes) para poder usar MinIO/R2 en vez de forzar una cuenta AWS real.
  • TekoApp-Backend/docker-compose.yml — servicio minio agregado.
  • TekoApp-Backend/.env (real, esta máquina) y .env.example (template) — MOBILE_CLIENT_SECRET, S3_ENDPOINT, S3_FORCE_PATH_STYLE cargados; el .env real ya apunta a MinIO local para S3.
  • TekoApp-Frontend-Mobile/dart_defines.local.json (gitignored) — valores listos para flutter run --dart-define-from-file=.
  • TekoApp-Backend/.claude/rules/database-conventions.md y TekoApp-Frontend-Mobile/openspec/decisions.md — decisión final de id/referenceId (exponer ambos siempre, ejecutar antes de publicar) y backlog de las 5 features grandes pedidas (propinas, calificaciones anónimas + KPIs, marco legal/tributario, branding centralizado) — documentadas, ninguna implementada todavía, cada una necesita su propia fase dedicada.
